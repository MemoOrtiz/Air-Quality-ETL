## Decoupling rules (R1–R3)

These are the root cause of the 8-month block and the criteria for accepting or
rejecting any new design.

- **R1 — No stage imports another.** Silver never does
  `from src.ingestion... import`.
- **R2 — The contract is the data at rest, not a function call.**
  `Bronze → bronze/ → Silver → silver/ → Gold → gold/`. There are no arrows
  between the *code* of the stages, only between code and storage.
- **R3 — Each stage runs alone and is idempotent.** Silver must be able to run
  over data ingested three weeks ago without touching Bronze, and running it
  five times gives the same result.

**R1 is not fully satisfied today:** there is `event_date` transformation logic
inside `ingestion/`, disabled but living in the wrong layer. D2 resolves it.

## Data conventions

**Bronze** — **raw JSON exactly as the API returns it**, immutable and
append-only. Partitioned **only** by `zone/ingest_date/sensor_id`. It is never
cleaned: deduplication belongs to Silver. The same measurement appearing under
two different `ingest_date=` partitions is **deliberate** — that is the audit
log working as intended.

**Silver** — Parquet (snappy), partitioned by `zone/event_date`. It is
**derivable and disposable**: regenerated from Bronze, which is why it **is not
immutable**. Full rebuild with overwrite by partition.

Two common traps:

- **Bronze stores JSON, not JSONL.** JSONL grouped by `event_date` is
  transformed output and therefore belongs to Silver by definition.
- **`ingest_date` is not `event_date`.** The first is when the data was
  fetched, the second when it was measured. Separating them is what makes
  backfills possible.

Real file schemas are in §4.5 of the master document. One detail that
constrains Silver: measurement `results[]` entries carry **no `id` field**, so
the deduplication key must be built from `sensor_id` +
`period.datetimeFrom.utc`.

## The two axes of parallelism

A distinction that gets confused often:

- **Across zones — it does not help.** The OpenAQ rate limit is **per API key**,
  not per process. Three runners each with their own limiter cannot coordinate:
  they split the same call budget and the ceiling does not move. Use
  `max-parallel: 1`; the value of a matrix here is **failure isolation**, not
  speed.
- **Within a zone — it does help.** `ThreadPoolExecutor(max_workers=4)` with a
  shared in-memory `RateLimiter`. The sequential pipeline underuses the budget
  (~46 of 55 req/min, waiting on responses). Real gain is ~20-25%, not linear.

The API is the bottleneck, not the code. No orchestration moves that ceiling;
only a higher limit negotiated with OpenAQ.

## Known debt

These are trade-offs, not oversights. Name them, do not hide them.

- **Credentials:** static access keys in `.env`. The correct approach on EC2/ECS
  is an IAM Role. Studied, not applied.
- **Small files:** one JSON per page is roughly 4,500 files per city per month.
  It hurts Spark and Athena. Defensible in Bronze for immutability and replay.
- **Sequential pipeline:** a deliberate decision that respects the rate limit.
- **`.env` is never committed.** It is in `.gitignore`.
